## Why

Main's reload test, on the previous runner image, already showed the futex rename. Run 45828696705 (main `931839cc`, 2026-11-26 13:26 UTC) panicked with `last wchan "futex_do_wait"`. Linux 6.17 renamed `futex_wait_queue` to `futex_do_wait`. Commit `91ca8e2c` accepts both names. On that same PR head, `cargo test` of `horbm` passed, including `reload` and `retrieve`. The futex assertion is not what kept #393 red.

The smoke failure is the ALSA flush measurement. The last green `router, gateway, pipeline` on main was run 45738785590 (image `20261116.376.1`, kernel `7.0.0-1017-azure`), where `alsa_flush_is_under_a_millisecond` passed and the live loop reported `barge_in_stop_ns=2113`. The 20261122 image's kernel is `7.0.0-1020-azure`. `AlsaOut::barge` waited for the callback with `sched_yield`. On that kernel the yield loop did not let the callback thread run inside 100 ms, so `flush_honor_ns` stayed empty and the test reported the flush as ignored. The null PCM itself still honors the flush once the callback is scheduled: the number the callback records is a couple of microseconds.

The package job failed because the GitHub Ubuntu image ships a Microsoft apt source this job does not use. `packages.microsoft.com` answered 403, and `apt-get update` treats that as a hard error. The router job's apt step happened to succeed on the same push. The next run can hit the same 403, so both workflows drop those source files before `apt-get update`.
